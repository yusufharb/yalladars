# خطة الإصلاح والتأمين الشاملة لتطبيق يلا درس — YallaDars (النسخة المعدّلة v2)

تستجيب هذه الخطة المعدّلة لجميع الملاحظات الـ 12 الواردة في تقرير المراجعة الهندسي والأمني، مع الالتزام الصارم بعدم تعديل أي ملف كود قبل اعتماد الخطة، وعدم تفعيل أي خدمات مدفوعة، والحفاظ على جميع البيانات والميزات الحالية، وترتيب الأولويات: **الأمن أولًا، ثم البيانات والمزامنة، ثم وظائف التطبيق، ثم أندرويد والاختبارات**.

## ثانيًا: المعمارية المستهدفة وتدفق الأمان والمزامنة

```
+-----------------------------------------------------------------------------------+
|                        الواجهة الأمامية (React SPA / Android WebView)              |
|                                                                                   |
|  +-----------------------+    +------------------------+    +------------------+  |
|  | شاشة الدخول والتسجيل  |    | طابور المزامنة المعلق  |    | طابور المرفوضات  |  |
|  | (بدون دخول تلقائي)    |    | yd_sync_queue_v2       |    | yd_sync_blocked  |  |
|  +-----------+-----------+    +-----------+------------+    +--------+---------+  |
|              |                            |                          ^            |
|              | JWT Bearer Token           | Push Changes             | Rejected   |
+--------------|----------------------------|--------------------------|------------+
               v                            v                          |
+-----------------------------------------------------------------------------------+
|                              خادم Express المؤمّن (server.ts)                      |
|                                                                                   |
|  1. طبقة المصادقة (JWT Middleware):                                               |
|     - التحقق من التوقيع (JWT_SECRET الإلزامي في الإنتاج) + تاريخ الانتهاء (exp)    |
|     - التحقق من وجود المستخدم في القاعدة وأن حالته (status !== 'suspended')        |
|                                                                                   |
|  2. طبقة التفويض وعزل البيانات (RBAC & Record-Level Isolation):                    |
|     - Pull (/api/sync/state): فلترة السجلات حسب الدور والعلاقة + حذف passwordHash  |
|     - Push (/api/sync/push): مصفوفة التحقق العلائقي الشاملة + منع تصعيد الصلاحيات |
|     - Linking (/api/parent/link): تحقق خادمي صارم من linkingCode + Rate Limiting  |
|     - Reset (/api/sync/reset): محصور بدور admin فقط + مسجل في auditLogs           |
|                                                                                   |
|  3. طبقة التخزين الذري والمتين (Atomic Persistence Layer):                        |
|     - متسلسلة كتابة (Write Lock) -> كتابة لـ db.json.tmp -> fs.renameSync ذري      |
|     - نسخة احتياطية تلقائية (db.json.bak) واستعادة آمنة عند اكتشاف تلف            |
+-----------------------------------------------------------------------------------+
```

## ثالثًا: خطة التنفيذ التفصيلية (مرتبة حسب الأولوية)

### المرحلة 1: الأمن والمصادقة وإدارة الجلسات (`server.ts`, `src/context/AuthContext.tsx`, `src/pages/LoginPage.tsx`, `.gitignore`)

1. **إدارة مفتاح `JWT_SECRET` والتحقق الصارم من التوكن (`server.ts`)**:
   - في بيئة الإنتاج (`process.env.NODE_ENV === 'production'`): اشتراط وجود `process.env.JWT_SECRET` بطول لا يقل عن 32 حرفًا؛ وإذا كان مفقودًا يرفض الخادم الإقلاع فورًا (Fail-Fast) برسالة خطأ واضحة.
   - في بيئة التطوير فقط (`NODE_ENV !== 'production'`): إذا لم يتوفر `process.env.JWT_SECRET`، يتم توليد مفتاح عشوائي وحفظه في `.local_jwt_secret` في جذر المشروع (خارج `/data` وخارج `/public`) مع إضافة `.local_jwt_secret` إلى `.gitignore` واستبعاده من أي مسار نسخ احتياطي أو تصدير.
   - تحديث دالة `verifyJwt` وميدلوير المصادقة للتحقق في كل طلب محمي من:
     1. صحة التوقيع الرقمي (`HMAC-SHA256`).
     2. عدم انتهاء الصلاحية (`exp > Date.now()`).
     3. وجود المستخدم الفعلي في قاعدة البيانات وأن حالته نشطة (`user.status !== 'suspended'`).

2. **الفصل التام بين تسجيل حساب جديد وتكملة الملف الشخصي وتسجيل الدخول (`server.ts`)**:
   - في `/api/auth/register`:
     - تطبيع البريد الإلكتروني (`email.trim().toLowerCase()`).
     - إذا كان البريد موجودًا مسبقًا في `db.users` (تحت أي ظرف، سواء كان يملك `passwordHash` أم لا)، يُرفض الطلب فورًا بكود **`409 Conflict`** دون تعديل `passwordHash` أو أي بيانات في الحساب القائم.
     - تقييد الأدوار المسموح بتسجيلها ذاتيًا عبر التسجيل العام بـ (`student`, `parent`, `teacher`, `assistant`) ومنع تسجيل دور `admin` عبر واجهة التسجيل العام.
   - فصل المسارات المحمية:
     - **تسجيل الدخول (`/api/auth/login`)**: يتحقق من البريد وكلمة المرور عبر `scrypt` والمقارنة الزمنية الثابتة `crypto.timingSafeEqual`.
     - **تكملة/تحديث الملف الشخصي (`/api/auth/profile`)**: يتطلب توكن جلسة صالحًا (`401` بدون توكن) ولا يسمح للمستخدم إلا بتعديل ملفه الشخصي هو فقط (`req.user.id === targetUserId`) مع منع تعديل الحقول الحساسة (`role`, `status`, `passwordHash`).
     - **تغيير كلمة المرور (`/api/auth/change-password`)**: يتطلب توكن جلسة صالحًا والتحقق من كلمة المرور الحالية قبل تعيين كلمة المرور الجديدة.

3. **إلغاء الدخول التلقائي في المتصفح الجديد وحماية وضع العرض التجريبي (`src/context/AuthContext.tsx`, `src/pages/LoginPage.tsx`)**:
   - تعديل `AuthContext.tsx` بحيث يبدأ التطبيق بحالة `currentUser = null` عند عدم وجود جلسة موثقة بتوكن صالح في `localStorage`، لفتح شاشة تسجيل الدخول افتراضيًا دون أي دخول تلقائي بحساب المدرس.
   - التحقق من صلاحية الجلسة عبر `/api/auth/me` عند بدء التشغيل؛ وفي حال انتهاء التوكن يتم توجيه المستخدم لشاشة الدخول مع الحفاظ على طابور التغييرات المحلية المعلقة دون مسحها.
   - إخفاء أزرار الحسابات التجريبية افتراضيًا في شاشة الدخول وإظهارها فقط عند تفعيل زر **"وضع العرض التجريبي (Demo)"**، مع تمرير مصادقة حقيقية عبر الخادم وإصدار JWT صالح.

4. **تقييد `/api/sync/reset` بدور المدير فقط (`server.ts`)**:
   - اشتراط مصادقة صالحة وأن يكون `req.user.role === 'admin'` حصريًا (`401` لغير المسجل، `403 Forbidden` لأي دور آخر بما فيه `teacher`).
   - في بيئة الإنتاج (`NODE_ENV === 'production'`): تعطيل التصفير الشامل لبيانات المستخدمين الفعليين (أو حصره بإعادة تهيئة حسابات العرض التجريبي فقط عند طلب المدير).
   - تسجيل كل عملية إعادة ضبط في `db.auditLogs` مع معرف المدير والطابع الزمني وعنوان الطلب.

### المرحلة 2: عزل البيانات الصارم وحماية المزامنة ومتانة القاعدة (`server.ts`, `src/services/syncEngine.ts`, `src/services/storage.ts`)

1. **متانة قاعدة البيانات والكتابة الذرية ومنع التلف (`server.ts`)**:
   - استبدال الكتابة المباشرة لملف `db.json` بطبقة تخزين ذرية متزامنة (`saveDbAtomically`):
     - استخدام طابور/قفل كتابة متسلسل (`writeQueue`) لمنع تداخل عمليات الكتابة المتزامنة.
     - كتابة البيانات أولًا إلى ملف مؤقت `data/db.json.tmp` ومزامنته على القرص (`fsync`)، ثم نسخ النسخة السليمة الحالية إلى `data/db.json.bak`، ثم تنفيذ `fs.renameSync('data/db.json.tmp', 'data/db.json')` الذري.
     - عند قراءة القاعدة (`loadDb`): إذا تعذر تحليل `db.json` بسبب انقطاع مفاجئ سابق، يستعيد الخادم تلقائيًا آخر نسخة سليمة من `db.json.bak` ويسجل الحدث دون فقدان البيانات.

2. **عزل البيانات الصارم حسب الدور والعلاقة وتجريد الأسرار (`getFilteredStateForClient` في `server.ts`)**:
   - **تجريد الأسرار إلزاميًا**: حذف `passwordHash` وأي حقول تحقق/أسرار من جميع كائنات `users` قبل إرسالها في `/api/sync/state` أو `/api/auth/*`.
   - **المدير (`admin`)**: يرى بيانات النظام اللازمة للإشراف الإداري وسجلات التدقيق.
   - **المدرس (`teacher`)**:
     - يرى فقط المجموعات التي يملكها (`group.teacherId === user.id`).
     - يرى فقط العضويات، الحضور، الواجبات، التقييمات، الدرجات، الإعلانات، الملاحظات، المدفوعات، المواد التعليمية، الاختبارات، تسليمات الاختبارات، الشهادات، الحصص المباشرة، وطلبات الانضمام المرتبطة بمجموعاته هو فقط.
     - يرى فقط ملفات الطلاب وأولياء الأمور والمساعدين المرتبطين بمجموعاته (أو الطلاب الجدد غير المنضمين بعد لتمكين البحث برمز الربط/الانضمام ضمن الضوابط)، ولا يرى مجموعات أو درجات أو مدفوعات مدرسين آخرين.
   - **المساعد (`assistant`)**:
     - يرى فقط المجموعات المسندة إليه (`assistantId === user.id` أو المرتبطة بالمدرس المشرف عليه ضمن نطاق المجموعات المحددة) والسجلات التشغيلية اللازمة لعمله (حضور، واجبات، درجات، طلبات انضمام)، دون صلاحيات إدارية مطلقة أو حذف مجموعات.
   - **الطالب (`student`)**:
     - يرى فقط ملفه الشخصي، والمجموعات المنضم إليها (`members` بحالة مقبولة)، والواجبات والمواد والاختبارات والإعلانات والحصص الخاصة بمجموعاته فقط.
     - في الجداول الفردية (`attendance`, `grades`, `payments`, `badges`, `certificates`, `quizSubmissions`, `joinRequests`): يرى **سجلاته هو فقط** (`studentId === user.id`) ولا يرى درجات أو مدفوعات أو حضور زملائه في نفس المجموعة.
     - في `notes`: يرى فقط الملاحظات الموجهة له وغير المخفية (`visibility === 'student_visible'` أو العامة الموجهة له)، ولا يرى `teacher_only`.
   - **ولي الأمر (`parent`)**:
     - يتم استخراج قائمة الأبناء المرتبطين به فعليًا عبر جدول `parentStudents` (`link.parentId === user.id`).
     - يرى فقط ملفات أبنائه المرتبطين، ومجموعاتهم، وحضورهم، ودرجاتهم، وواجباتهم، ومدفوعاتهم، وشهاداتهم، والملاحظات الخاصة بهم ذات الصلاحية (`visibility === 'parent_visible'` أو `'public'`). لا يرى أي طالب غير مرتبط به ولا الملاحظات السرية للمدرس (`teacher_only`).

3. **تأمين `/api/sync/push` والتحقق الشامل من الملكية والعلاقات (`server.ts`)**:
   - **منع الدفع بدون مصادقة**: إزالة استثناء قاعدة البيانات الفارغة نهائيًا؛ كل طلب `/api/sync/push` بدون JWT صالح يُرفض فورًا بكود `401 Unauthorized`.
   - **منع تصعيد الصلاحيات**: منع أي مستخدم غير `admin` من تعديل حقل `role` أو `status` في جدول `users` أو إنشاء حساب بدور `admin`.
   - **مصفوفة التحقق العلائقي قبل تطبيق أي تغيير (`upsert` أو `delete`)**:
     - `groups`: الإنشاء والتعديل والحذف للمدرس المالك (`group.teacherId === user.id`) أو `admin` فقط.
     - `members`, `attendance`, `homework`, `assessments`, `grades`, `announcements`, `notes`, `payments`, `materials`, `badges`, `quizzes`, `certificates`, `liveSessions`: التحقق من أن المستخدم هو المدرس المالك للمجموعة المرتبطة بالسجل (أو المساعد المفوض للمجموعة في العمليات التشغيلية المسموحة فقط، مع منع المساعد من حذف المجموعات أو تعديل المدفوعات الإدارية إذا لم يكن مفوضًا).
     - `quizSubmissions`: يُسمح للطالب بإنشاء/تحديث تسليمه هو فقط (`studentId === user.id`) لاختبار ينتمي لمجموعة هو عضو فعلي فيها، ويُسمح للمدرس المالك للمجموعة برصد/تعديل الدرجة.
     - `joinRequests`: يُسمح للطالب بإنشاء طلب انضمام لنفسه فقط (`studentId === user.id`)، ويُسمح للمدرس المالك للمجموعة (أو مساعده المفوض) بقبول/رفض الطلب.
     - `users`, `studentProfiles`, `teacherProfiles`: كل مستخدم يعدل ملفه الشخصي فقط (`id === user.id` أو `userId === user.id`)، مع السماح للمدرس بتحديث البيانات الأكاديمية المسموحة لطلابه ضمن مجموعاته فقط دون المساس ببيانات الحساب والمصادقة.
     - `parentStudents`: منع الإنشاء الحر عبر `push` المباشر بدون التحقق الصارم من كود الربط (`linkingCode`) المطابق للطالب الهدف.

4. **تأمين ربط ولي الأمر بالطالب عبر الكود (`server.ts`, `src/pages/ParentDashboard.tsx`)**:
   - توفير مسار خادمي مخصص ومؤمّن `/api/parent/link-student` (بالإضافة إلى التحقق داخل `push`):
     - يستقبل `linkingCode` من ولي الأمر المصادق عليه.
     - يطبق حماية ضد التخمين (Rate Limiting لكل حساب/عنوان IP).
     - يبحث في الخادم عن `studentProfiles` التي تطابق `linkingCode` بدقة (بعد التطبيع `trim().toUpperCase()`).
     - يتحقق من أن الكود صالح وغير ملغى، وأن الطالب موجود فعليًا في `users` بدور `student`.
     - ينشئ سجل `parentStudents` بمعرف مركب فريد `ps_${parentId}_${studentId}`، ويعيد بيانات الطالب المرتبط ومجموعاته ودرجاته فورًا لولي الأمر.
   - في `src/services/storage.ts` و `mockInitialData.ts`: ضمان توليد `linkingCode` فريد وحتمي غير متصادم لكل طالب (مثل `YD-LK-1001` لأحمد حمدي في البيانات الأولية، وأكواد فريدة مشتقة من معرف الطالب + لاحقة عشوائية محققة من عدم التكرار للطلاب الجدد).

5. **حماية طابور المزامنة المحلي ومنع الحذف الصامت (`src/services/syncEngine.ts`)**:
   - فصل حالة الطابور المحلي إلى مخزنين دائمين في `localStorage`:
     1. **`yd_sync_queue_v2` (طابور الانتظار النشط)**: يحتفظ بالتغييرات التي لم تُرسل بعد أو التي فشلت بسبب انقطاع الشبكة أو الخادم (`5xx` / Network Error) ليتم إعادة محاولتها تلقائيًا عند عودة الاتصال.
     2. **`yd_sync_blocked_v2` (طابور التغييرات المرفوضة/المعلقة)**: عند رد الخادم بـ `rejectedChanges` (بسبب صلاحيات `403` أو تعارض علائقي `400`)، **لا يتم حذف التغيير بصمت**، بل يُنقل من الطابور النشط إلى `yd_sync_blocked_v2` مرفقًا بطابع زمني وسبب الرفض الصريح القادم من الخادم (`reason`).
   - حذف العناصر من `yd_sync_queue_v2` يقتصر حصريًا على المعرفات الواردة في `appliedChangeIds` المؤكدة من الخادم.
   - عند انتهاء صلاحية الجلسة (`401 Unauthorized`): يتوقف محرك المزامنة عن الإرسال مؤقتًا ويحتفظ بكامل محتويات `yd_sync_queue_v2` دون مسحها حتى يعيد المستخدم تسجيل الدخول، مع إشعار واضح في الواجهة.
   - إضافة مؤشر وواجهة معاينة في التطبيق تعرض للمستخدم حالة المزامنة وأي عناصر في `yd_sync_blocked_v2` مع سبب رفضها وإمكانية مراجعتها أو التراجع عنها.

### المرحلة 3: استكمال رحلات الأدوار الأربعة وماسح QR (`src/components/QRScannerModal.tsx`, شاشات الأدوار)

1. **مكون مسح QR الحقيقي بالكاميرا (`src/components/QRScannerModal.tsx`)**:
   - دعم القراءة الحية عبر `BarcodeDetector` الأصلي في المتصفحات الداعمة مع fallback تلقائي لمكتبة `html5-qrcode`.
   - معالجة حالات رفض صلاحية الكاميرا أو عدم وجود كاميرا أو العمل في بيئة غير آمنة بإظهار رسالة عربية واضحة وتوفير **الإدخال اليدوي الاحتياطي** للكود فورًا دون تعطل الشاشة.
   - تنظيف وإغلاق مسار الفيديو (`MediaStreamTrack.stop()`) فور إغلاق النافذة أو نجاح القراءة.

2. **رحلة الأدوار الأربعة (المدرس، المساعد، الطالب، ولي الأمر)**:
   - التأكد من اكتمال دورة العمل لكل دور ضمن حدود صلاحياته المعزولة:
     - **المدرس**: إنشاء وإدارة المجموعات، قبول الطلاب، تسجيل الحضور بمسح QR أو يدويًا، إنشاء الواجبات والاختبارات، رصد الدرجات، إصدار الشهادات، متابعة المدفوعات، وإدارة المساعدين.
     - **المساعد**: الوصول للمجموعات المسندة إليه، تسجيل الحضور، متابعة الواجبات وطلبات الانضمام ضمن صلاحياته.
     - **الطالب**: التسجيل، الانضمام للمجموعات، عرض بطاقة QR وكود ربط ولي الأمر، حل الاختبارات، متابعة الحضور والدرجات والواجبات والشهادات الخاصة به فقط.
     - **ولي الأمر**: التسجيل، ربط الابن عبر `linkingCode` الموثق على الخادم، ومتابعة حضور ودرجات وواجبات ومدفوعات وملاحظات أبنائه المرتبطين فقط.

### المرحلة 4: استكمال وتأمين مشروع Android الهجين (`android/`)

1. **توضيح المعمارية في الكود والتوثيق**:
   - يعتمد مجلد `android/` معمارية **تطبيق أندرويد هجين (Secure WebView Hybrid Wrapper)** بلغة Kotlin يعرض تطبيق الويب المتجاوب مع تكامل أصلي للكاميرا والتخزين، وهو الخيار الأنسب لضمان التطابق الوظيفي الكامل 100% مع نسخة الويب دون ازدواجية في قواعد البيانات أو الشاشات (مقابل إعادة كتابة تطبيق Native Compose منفصل كليًا).

2. **استكمال ملفات البناء (`android/settings.gradle.kts`, `android/gradle.properties`, `android/app/build.gradle.kts`)**:
   - استكمال تعريف المستودعات (`google()`, `mavenCentral()`) وإعدادات Gradle وملف `proguard-rules.pro` وموارد التطبيق الأساسية ليكون المشروع قابلًا للفتح والبناء في Android Studio.
   - جعل رابط الخادم (`SERVER_URL`) قابلًا للتهيئة عبر `BuildConfig` في `android/app/build.gradle.kts` (في بيئة `debug` يشير إلى خادم التطوير المحلي، وفي بيئة `release` يشير إلى نطاق الإنتاج الآمن `https://`).

3. **تأمين `AndroidManifest.xml` و `MainActivity.kt`**:
   - **منع `cleartextTraffic` في الإنتاج**: ضبط `android:usesCleartextTraffic="false"` في البيان الرئيسي (`main/AndroidManifest.xml`)، وقصر السماح بـ HTTP المحلي على ملف تكوين أمان الشبكة الخاص ببيئة التطوير (`debug`) فقط.
   - **تأمين صلاحية الكاميرا في `WebChromeClient.onPermissionRequest`**:
     - إزالة المنح التلقائي غير المشروط (`request.grant`).
     - التحقق أولًا من أن أصل الطلب (`request.origin`) يطابق نطاق التطبيق الموثوق (`SERVER_URL`).
     - التحقق من أن المورد المطلوب هو الكاميرا (`RESOURCE_VIDEO_CAPTURE`) فقط، ثم فحص صلاحية أندرويد `Manifest.permission.CAMERA` وقت التشغيل عبر `ActivityResultContracts.RequestPermission`؛ ولا يتم استدعاء `request.grant( arrayOf(PermissionRequest.RESOURCE_VIDEO_CAPTURE) )` إلا بعد موافقة المستخدم الفعلية في نظام أندرويد.
   - **حماية `WebView`**: تعطيل الوصول غير الضروري للملفات الحساسة (`allowFileAccessFromFileURLs = false`, `allowUniversalAccessFromFileURLs = false`) وحصر التصفح الداخلي بالنطاق الموثوق للتطبيق.
